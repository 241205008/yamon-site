# 判断記録（技術選定・仕様の解釈）

優先順位は「1. 各画面のデザイン（Figma Make のスクリーンショット）」「2. SPEC.md の MVP」「3. その他」。
SPEC.md のコンポーネント構成・技術選定は参考扱いとし、変えた点はここに理由と他の選択肢を書く。

---

## D1. UI ライブラリ：shadcn/ui を使わず Tailwind CSS ＋ lucide-react で直接書く

- **採用理由**：デザインのスクリーンショットは Tailwind の標準色・角丸・影でそのまま再現できる。使う部品はボタン・入力・モーダル・バッジ程度で、shadcn/ui の CLI 導入と Radix 依存を増やすほどの量がない。
- **他の選択肢**
  - shadcn/ui（SPEC.md の記載）：アクセシビリティの面では有利。ただしコードの生成量が増え、デザインに合わせて上書きする手間がかかる。部品が増えたら後から移行できる。
  - MUI などのコンポーネントライブラリ：見た目がデザインから離れるため不採用。

## D2. 地図：Leaflet ＋ OpenStreetMap（react-leaflet）

- **採用理由**：デザインの地図は CSS グラデーションの疑似マップだが、SPEC.md 7章 #16 で「疑似実装、要差し替え」とされている。疑似マップでは実際の位置関係が分からず、記録の位置を正しく見られない。デザインの要素（カード枠、左上の「マップビュー／中心座標」、右下の凡例、赤いピン、青い件数バッジ）はそのまま残し、背景だけ実際の地図にした。
- **他の選択肢**
  - 疑似マップのまま：見た目はデザインと完全に同じになるが、座標を % に変換する方式では地図として使えない。
  - Google Maps / Mapbox：API キーと課金設定が必要。招待制・約100人の規模では過剰。
- **注意**：地図タイルの読み込みにはネット接続が必要。OSM のタイル利用規約上、大量アクセスするならタイル配信元の変更を検討する。

## D3. データ永続化：localStorage に1つの JSON（`yamon:db:v1`）として保存

> **置き換え済み**：バックエンド版では D14（下記）・D17（下記） に置き換える（2026-10-13 採用）。

- **採用理由**：SPEC.md の指定（バックエンドなし）に従う。全データを1キーにまとめ、`version` を持たせて将来の移行に備えた。別タブでの変更は `storage` イベントで反映する。
- **データ構造で SPEC.md から変えた点**（いずれも SPEC.md 7章の「既知の問題」への対応）
  - 観察記録を観察会にネストせず、独立した配列にして `eventId` で紐付け（#7）
  - 生き物を名前ではなく `creatureId` で参照（#6）。改名すると既存記録にも自動で反映される
  - ID は `crypto.randomUUID()`（#8）
  - `month` / `timeOfDay` は保存せず `date` / `time` から導出（#9）
  - 座標がない記録は `lat/lng = null`（`0,0` で表さない）。場所の種類は `locationType`（`main` / `other` / `none`）で持つ（#10）
- **制約**：localStorage はブラウザごと・端末ごとに別。容量はおおむね 5MB で、1件 300 バイトとして 1.5 万件前後が上限の目安。保存に失敗したら画面にエラーを出す。10年以上の運用・複数端末での共有にはバックエンドへの移行が必要。
- **他の選択肢**：IndexedDB は容量が大きいが、非同期 API でストア層が複雑になる。プロトタイプの段階では localStorage を選び、移行しやすいようにデータ操作を `src/lib/store.ts` に集約した。

## D4. 認証：PBKDF2 でハッシュ化したパスワード＋localStorage のセッション
> **置き換え済み**：バックエンド版では D18（下記） に置き換える（2026-10-13 採用）。

- **採用理由**：localStorage に平文のパスワードを残さないため、Web Crypto の PBKDF2-SHA256（10万回、ユーザーごとのソルト）でハッシュ化した。セッションは `yamon:session` にユーザー ID を保存する。無効化されたユーザーは、セッションが残っていてもログアウト扱いにする。
- **限界**：バックエンドがないため、ブラウザの開発者ツールで localStorage を書き換えれば権限は偽装できる。これは「バックエンドなし」という前提の限界で、本番運用ではサーバー側での認証が必須。
- **他の選択肢**：SHA-256 を1回かけるだけの方式は総当たりに弱いため不採用。

## D5. 招待メール：自動送信せず、招待リンクを表示して管理者が渡す
> **置き換え済み**：バックエンド版では招待メールを自動送信する（D19（下記）、2026-10-13 採用）。

- **採用理由**：バックエンドがないとメールを送れない。招待作成後に `/login?invite=<token>` のリンクを表示し、「リンクをコピー」と「メールアプリで送る」（`mailto:`）を用意した。
- **トークン**：UUID、有効期限48時間。再送信するとトークンを作り直して期限を延ばし、古いトークンは使えなくする。同じアドレスへ再度招待した場合も古い未使用トークンを無効にする。期限切れの判定は保存せず、`expiresAt` から導出する。
- **他の選択肢**：EmailJS などの外部送信サービスは API キーをフロントに置くことになるため不採用。

## D6. 最初の管理者：デモデータとして作成
> **置き換え済み**：バックエンド版では、セットアップ用トークンが必要な初回セットアップ画面にする（D18（下記）・[MVP](MVP.md)、2026-10-13 採用）。

- **採用理由**：招待制なので、最初の1人は誰かが用意する必要がある。初回起動時に `admin@example.com` を作成する（README 参照）。
- **他の選択肢**：初回だけ表示する「管理者セットアップ画面」。デザインにない画面のため今回は見送った。本番化するときはこちらに置き換えるべき。

## D7. 管理者移譲の取り消し：移譲元本人がホーム画面から行う

- **背景**：SPEC.md では管理者画面に取り消しボタンがあるが、移譲すると移譲元は一般ユーザーになり、管理者画面に入れない。また、SPEC.md 7章 #5 で「操作者検証がない」と指摘されている。
- **採用**：取り消せるのは移譲元のユーザー本人だけで、期限は1時間。移譲元がホーム画面を開くと、残り時間つきの「移譲を取り消す」バナーを表示する。管理者画面の移譲履歴には状態（残り時間／確定／取り消し済み）を表示する。移譲先がさらに別の人へ移譲していた場合は、取り消すと管理者が2人になるため取り消せない。
- **他の選択肢**：新しい管理者が取り消す方式。新管理者が自分で権限を返すだけで「取り消し」の意味が薄いため不採用。

## D8. 「場所を指定しない」でも生き物の選択は表示する

- **背景**：SPEC.md では「場所を指定しない場合は生き物選択を非表示」とある。
- **採用**：生き物の選択は常に表示し、必須にした。生き物のない記録は、一覧・地図・場所別のどこにも意味のある形で出せず、データとして使えないため。元のプロトタイプの不具合だった可能性が高いと判断した。
- **他の選択肢**：仕様どおり非表示にし、生き物なしの記録を許す。用途がはっきりしたら見直す。

## D9. 生き物の削除：記録がある場合は削除できない

- **採用理由**：記録は `creatureId` で参照しているため、削除すると記録が宙に浮く。10年以上の運用を考え、記録が1件でもあれば削除を拒否し、件数を表示する。改名は可能。
- **他の選択肢**：記録ごと削除する（データを失う）、論理削除する（UI が複雑になる）。

## D10. 日時は JST 固定

- `toISOString()`（UTC）を使うと、JST の 0〜9 時に前日の日付になる（SPEC.md 7章 #14）。今日の日付・現在時刻・表示用の日時は、端末のタイムゾーンに関係なく JST で計算する（`src/lib/time.ts`）。

## D11. ルーティング：React Router v7 の `react-router` パッケージ（宣言的ルーティング）

- `location.state` でのデータ受け渡しをやめ、各画面はストアを直接読む（SPEC.md 7章 #18）。観察会詳細は `/event-detail/:eventId` とし、再読み込みや URL 共有で表示が消えないようにした。
- `RequireAuth` / `RequireAdmin` のルートガードで、未ログインは `/login` へ、一般ユーザーの `/admin` はホームへ戻す。

## D12. ページング：「さらに表示」方式

- 観察会一覧・観察会詳細は20件ずつ、生き物管理は30件ずつ表示する。ホームの「最近の記録」は SPEC.md どおり最大10件。地図はピンを地点ごとにまとめるので、ページングしない。
- **他の選択肢**：仮想スクロール（react-window など）は、数千件規模になるまでは不要と判断した。

## D13. デザインに合わせた細部

- 記録フォームの「場所の種類」の初期値は、デザインに合わせて「その他の場所」。観察会詳細から追加する場合は、観察会の場所（主な場所／その他の場所名／座標）と日付を初期値にする。ただし観察会が未来の日付なら、観察日は今日を初期値にする（観察日に未来は選べないため）。
- 記録を編集するときは、日付を「日付を指定」で固定して開く。「今日」モードのままだと、日付をまたいで保存したときに記録の日付が変わってしまうため。
- ログイン中に招待リンクを開いた場合は、ホームへ飛ばさず「ログアウトして登録」を案内する。
- 観察会一覧の統計（観察記録数・生き物の種類）は、観察会に紐付いた記録だけで数える（デザインの数値と一致）。
- 背景は緑〜青のグラデーション。管理者画面のみ紫寄り（デザインどおり）。

# フロントエンド・バックエンド分離版（D14〜）

前提は [docs/MVP.md](MVP.md)（2026-10-13 合意）。費用は無料枠の範囲、利用者約100人、10年以上の運用、スマホが主な利用環境。
調査の経緯は [Issue #6](https://github.com/241205008/yamon-site/issues/6)。

**状態：採用（2026-10-13、ユーザー合意）。** 推奨案A（Cloudflare Pages ＋ Cloud Run ＋ Neon）を採用した。置き換わる D3〜D6 には「置き換え済み」の印を付けた。

料金・制限は 2026-10 時点で各サービスの公式ドキュメントと解説記事から確認したもの。無料枠は変わりやすいので、実装の着手時にもう一度確認する。

## D14. 全体構成：フロント（静的 SPA）＋ API サーバー＋ Postgres の3つに分ける

```
ブラウザ ──> Cloudflare Pages（React SPA）
               └ /api/* を同じオリジンのまま転送（Pages Functions）
                    └──> Google Cloud Run（Hono の API サーバー）
                              ├──> Neon（PostgreSQL）
                              └──> メール送信サービス
```

- **採用理由**：MVP の条件（無料・10年運用・パスワード認証・メール送信）をすべて満たす組み合わせのうち、特定のサービスへの依存が一番小さい。API は普通の Node.js コンテナ、DB は標準の PostgreSQL なので、どちらかの無料枠がなくなっても移し替えられる。
- **比較した案**

| 案 | 構成 | 無料で運用できるか | 判断 |
|---|---|---|---|
| A（採用） | Cloudflare Pages ＋ Cloud Run ＋ Neon | できる。Cloud Run は月200万リクエスト、Neon は 0.5GB・月100 CU 時間まで無料 | 採用。初回アクセス時に API と DB の起動待ち（数秒）がある |
| B | Cloudflare Pages ＋ Workers ＋ D1 | 条件付き。Workers Free は1リクエストあたり CPU 10ms までで、安全な強度のパスワードハッシュ（PBKDF2 数十万回、Argon2id）が収まらない。$5/月の Workers Paid なら問題ない | 次点。月$5を払えるなら、構成が1社で済み起動待ちもないので B が一番簡単 |
| C | Supabase（BaaS） | 実質できない。無料プロジェクトは7日間アクセスがないと一時停止する。観察会のない時期に止まる。止まらない Pro は $25/月 | 不採用。また、バックエンドを自分で実装する形にならない |
| D | Firebase（Firestore ＋ Cloud Functions） | Functions には従量課金の Blaze プラン（カード登録）が必要。Firestore は NoSQL で、統計や地点ごとの集計を書きにくい | 不採用 |
| E | Render（Web サービス＋Postgres） | できない。無料 Postgres は作成30日後に使えなくなり、14日後にデータごと削除される。バックアップもない | 不採用 |
| F | Vercel（Hobby）の Functions ＋ Neon | できる。ただし Hobby は非商用限定で、上限に達するとデプロイ全体が止まる | 不採用。将来、会費の徴収などを始めると規約に触れる可能性がある |

- **既知のリスク**
  - Cloud Run の無料枠を使うには、Google Cloud の請求先アカウント（クレジットカード）の登録が必要。予算アラートを設定して、課金に気づけるようにする。
  - Neon も Cloud Run もアクセスがないと停止する。止まった後の最初のアクセスは数秒遅い。
- **再検討する条件**：初回の待ち時間が現場で問題になったとき、または月$5程度を払えるようになったときは、案Bを再検討する。

## D15. フロントエンド：既存の React + Vite + TypeScript を流用し、Cloudflare Pages に置く

- **採用理由**：7画面はデザインどおりに作ってあり、動作も確認済み。書き直すとデザインの再現と動作確認をやり直すことになる。変えるのはデータの取得・保存だけで、`src/lib/store.ts` の中身を API 呼び出しに差し替える。サーバーとの通信状態（読み込み中・エラー・再取得）の管理には TanStack Query を足す。
- **ホスティング**：Cloudflare Pages。静的ファイルの配信は無料・無制限で、商用利用の制限もない。`/api/*` へのアクセスは Pages Functions で Cloud Run へ転送する。こうするとブラウザから見て画面と API が同じドメインになり、ログイン用の Cookie が Safari などの「サードパーティ Cookie のブロック」に引っかからない。
- **比較した案**
  - Next.js に書き換える：ログイン必須のアプリなので、サーバーサイドレンダリングによる表示速度や SEO の利点がほとんどない。書き換えの手間に見合わない。
  - Vercel / Netlify：使えるが、Vercel Hobby は非商用限定（D14 案F）。Netlify は無料枠の利用量に上限がある。
  - GitHub Pages：SPA の URL 直アクセス（例：`/event-detail/xxx` の再読み込み）がそのままでは動かない。API への転送もできない。

## D16. バックエンド：TypeScript ＋ Hono ＋ Drizzle ORM（Node.js、Cloud Run 上）

- **言語に TypeScript を選んだ理由**：フロントと同じ言語にして、入力チェックの定義（zod）と型を共有できる。1人で開発するので、2言語を行き来しない方がミスが少ない。
- **フレームワークに Hono を選んだ理由**：軽く、Node.js でも Cloudflare Workers でも同じコードが動く。将来 D14 案B（Workers）へ移るときも書き直しが少ない。
- **ORM に Drizzle を選んだ理由**：SQL に近い書き方で、生成される SQL が予想しやすい。PostgreSQL と SQLite（D1）の両方に対応する。マイグレーション（テーブル定義の変更履歴）も管理できる。
- **比較した案**
  - Express：実績は多いが、型の付き方が弱く、Workers では動かない。
  - NestJS：この規模には仕組みが重い。
  - Python（FastAPI）・Go：フロントと型を共有できず、2言語の保守になる。
  - Prisma：多機能だが、生成物が大きく、Cloud Run の起動時間が延びやすい。
- **テスト**：Vitest。API のテストには PGlite（WebAssembly 版の PostgreSQL）を使い、Docker なしで本物に近い DB で確かめる。

## D17. DB：PostgreSQL（Neon の無料プラン）

- **採用理由**：標準の PostgreSQL なので、10年の間にサービスを替えても `pg_dump` でそのまま移せる。統計（観察会ごとの件数、場所ごとの種類数）は SQL の集計で素直に書ける。無料枠（0.5GB）は、記録1件あたり数百バイトとして数十万件以上入るので、100人の規模なら当面足りる。
- **バックアップ**：無料プランで戻せる期間は短いので、GitHub Actions で定期的に `pg_dump` を取り、別の保存先に残す（後続 Issue で保存先を決める）。
- **比較した案**
  - Cloudflare D1（SQLite）：無料で 5GB まで。ただし D14 案B を前提にした選択肢。
  - Supabase / Render の Postgres：D14 の表のとおり、無料では運用できない。

## D18. 認証：自前のセッション認証（HttpOnly Cookie ＋ DB のセッション表）、パスワードは Argon2id

- **採用理由**：招待制、管理者権限の移譲、無効化したユーザーを即座にログアウトさせる、といった独自のルールが多い。汎用の認証サービスに合わせるより、セッション表を自分で持つ方が単純になる。
  - パスワードは Argon2id でハッシュ化する（OWASP の推奨）。
  - セッション ID は推測できない乱数にし、DB にはハッシュ値だけを保存する。
  - Cookie は `HttpOnly; Secure; SameSite=Lax` を付ける。
  - 招待トークンとパスワード再設定トークンも、DB にはハッシュ値で保存する。
  - 初回の管理者セットアップは、環境変数で渡すセットアップ用トークンを知っている人だけが実行できるようにする（ユーザーが0人のときに誰でも管理者になれる状態を作らない）。
- **比較した案**
  - Better Auth などの認証ライブラリ：メールとパスワードのログインや再設定はすぐ作れる。ただし招待制や管理者移譲は結局自分で書くことになり、ライブラリのテーブル構成に合わせる手間が増える。
  - Firebase Authentication / Supabase Auth：D14 で各サービスを採用しないため不採用。
  - JWT を localStorage に保存する：XSS（悪意あるスクリプトの埋め込み）でトークンを盗まれやすく、無効化もすぐには効かない。

## D19. メール送信：Resend（無料：1日100通・月3,000通）

- **採用理由**：送るのは招待と再設定のメールだけなので、100人規模なら無料枠に十分収まる。API が単純で、Node.js から1行で送れる。
- **前提**：送信元にする独自ドメイン（年1,000〜2,000円程度）が必要。迷惑メール扱いを避けるため、ドメインの認証（SPF・DKIM）を設定する。
- **比較した案**
  - Gmail の SMTP（アプリパスワード）：独自ドメインは不要。ただし個人の Gmail アカウントに依存し、10年の運用で管理者が替わったときに引き継ぎにくい。
  - Brevo（旧 Sendinblue）：無料で1日300通。ドメインなしでも送れるが、迷惑メールに入りやすい。
  - Amazon SES：安いが、利用開始時の審査があり、AWS アカウントの管理が増える。
- **決定（2026-10-13）**：独自ドメインを取得する。登録先は D21 を参照。

## D20. リポジトリ構成：1つのリポジトリにフロントとバックを置く（npm workspaces）

```
apps/web      フロントエンド（いまの src/ を移す）
apps/api      バックエンド（Hono）
packages/shared  入力チェック（zod）・型・固定マスター（主な場所・カテゴリ）
```

- **採用理由**：API の入力と出力の型を、フロントとバックで同じ定義から使える。片方だけ変えて壊れるのを型チェックで防げる。CI・Issue・PR も1か所で済む。
- **比較した案**：フロントとバックを別のリポジトリにする。デプロイは独立させやすいが、型の共有にパッケージ公開などの手間がかかる。1人開発では利点が小さい。デプロイは、同じリポジトリのまま `apps/web` と `apps/api` で別々に行う。

## D21. 運営の引き継ぎ：大学サークルへ委託できるようにアカウントを作る

- **背景**：今は個人開発だが、今後は大学のサークルに運営を委託する予定（2026-10-13 ユーザーより）。支払い（Google Cloud のカード、ドメイン代）と管理権限を、後からサークル側へ移せるようにしておく。
- **方針**
  - 各サービスの持ち主は、最初からプロジェクト専用のメールアドレス（例：やもんサイト用の Google アカウント）で作る。個人のアカウントと混ぜない。
  - 管理者は1人にせず、各サービスの「メンバー招待」の機能で後継者を追加できる形にする。
  - パスワードや Secret は、引き継ぎ時に変更・再発行できるよう一覧にしておく（実値はリポジトリに書かない）。
- **サービスごとの移し方**

| サービス | 支払い・持ち主の移し方 | 根拠 |
|---|---|---|
| Google Cloud（Cloud Run） | 請求先アカウント（カード）は、プロジェクトとは別に管理されている。サークル側で新しい請求先アカウントを作り、プロジェクトの「請求先を変更」で付け替える。サービスは止まらず、切り替えた日を境に請求先が分かれる。管理権限は IAM でサークルのメンバーをオーナーに追加する | [Google Cloud：プロジェクトの請求先の変更](https://docs.cloud.google.com/billing/docs/how-to/modify-project) |
| ドメイン | Cloudflare Registrar で取得する。原価で更新でき、Pages と同じ管理画面で DNS を管理できる。Cloudflare アカウント間でドメインを移せる（移す先のアカウントの承認が必要、取得から10日以上経過、移動後30日は再移動不可）。DNS 設定は移動先で作り直す | [Cloudflare：アカウント間のドメイン移動](https://developers.cloudflare.com/registrar/account-options/inter-account-transfer/) |
| Cloudflare Pages | アカウントにメンバーを招待して権限を渡す | — |
| Neon | Organization にメンバーを招待する。無料プランのため支払いはない | — |
| Resend | チームにメンバーを招待する。無料プランのため支払いはない | — |
| GitHub | リポジトリをサークルの Organization へ移す（Transfer）。Issue・PR・履歴はそのまま残る | — |

- **比較した案（ドメインの登録先）**
  - Namecheap：アカウント間で無料で移せる（Change Ownership）。ただし DNS の管理画面が Cloudflare と分かれる。
  - お名前.com など国内の登録業者：日本語で手続きできるが、更新料が初年度より高くなることが多く、オプションの勧誘も多い。
- **注意**：サークルは法人ではないことが多く、カードは代表者個人の名義になりやすい。代表者が卒業するたびに支払い元を付け替える手順を、引き継ぎ資料に残す（後続 Issue）。
